# Azure SQL Certification Threat Model

**Status:** Amended for the reviewed D-022 through D-029 first-manual managed-risk requirements. `GATE-01` is Ready (134 normative requirements and 53 acceptance criteria); this model is awaiting independent `GATE-02` review and is not accepted or ratified.

## Current Deployed State - D-033/D-034 Amendment

**Current status:** The owner has manually deployed the fixture. The dedicated logical server has public network access enabled behind exactly one firewall rule for one exact client address. Its Microsoft Entra-only administrator is the dedicated security Group containing the intended user. The fixed database is Basic and Online. No DACPAC has been applied, no trusted connection/authentication configuration has been established, and no Azure SQL test has run.

**Historical context:** D-033 replaced the prior agent-led activation and predeployment-gate route with owner-manual Azure actions. Earlier language naming an individual User as the SQL administrator, or presenting predeployment gates as the current operational path, is historical evidence only; it does not describe the deployed Group-admin fixture or grant authority.

**Active pre-test boundary:** Before a DACPAC publish or any test connection, verify only: trusted Microsoft Entra authentication; that no secret is committed, logged, or otherwise persisted; TLS with certificate validation; the exact intended server and database target; and least-privilege database permissions for the planned operation. These checks do not authorize mutation; D-033's human-execution boundary remains in effect.

## Scope And Authority

This model defines the security envelope for the Azure SQL Gate 2 certification fixture. It covers the settled subscription-scoped deployment into dedicated `example-test-rg`, the dedicated `example-test-sql` server, fixed `ProphetsWay.Example` database, public exact-address access, durable multi-wave lifecycle, ledger-bound disposable databases, and the one first-manual managed-risk exception.

It does not authorize Azure access, a deployment, DACPAC application, database access, test execution, recovery, cleanup, teardown, spend, current pricing selection, or owner ratification. Exact protected tenant, subscription, principal, address, timestamp, attempt, approval, and evidence values remain outside this document. It is a design requirement, not an implementation assessment.

**Authoritative anchors:** `D-001` through `D-029`; `U-001` through `U-008`; `SYS-01` through `SYS-29`; `HAR-01` through `HAR-33`; `INF-01` through `INF-27`; `OWN-01` through `OWN-19`; `GATE-01` through `GATE-18`; and `AC-01` through `AC-53` in [../azure-sql-certification-requirements.md](../azure-sql-certification-requirements.md), with decisions in [../decision-log.md](../decision-log.md).

## System And Assets

The fixture is one subscription-scoped deployment that creates a dedicated resource group and invokes resource-group-scoped modules to create one logical server, one exact-address firewall rule, and one fixed database. The fixed database receives the reviewed DACPAC, retains synthetic baseline data, and persists across independently authorized waves. It is never a disposable test-store identity.

The Fixture-Lifetime Control Authority is the sole logical provenance and lifecycle authority from deployment-number reservation through verified final teardown. It holds append-only revisions, burned deployment numbers, active target-binding and baseline-manifest digests, fixed-database state/cause, attempt records, unresolved operations, and survivor dispositions. Its availability and integrity are security-critical: ambiguity, unavailability, a broken chain, two active revisions, or disagreement with retained evidence makes the fixture `Unreconciled`.

## Actors And Identity Separation

| Actor | Trust level and permitted purpose | Explicit limit |
| --- | --- | --- |
| Owner | Trusted approval, activation, daily-monitoring, incident-acknowledgement, and logical-server Microsoft Entra administrator authority | D-022 lets the owner's human Entra user operate only for one active first-manual aggregate identity; this neither creates standing automation authority nor merges operation approvals. |
| First-manual operator | The same human Entra user performs each separately approved ARM, DACPAC, fixed-data, and lifecycle operation through interactive Azure CLI sign-in and supported local `Active Directory Default` | ARM and SQL authority remain separated. Copied tokens, SQL authentication, passwords, client secrets, embedded credentials, UAMI, persistent additional owner SQL grants, another aggregate identity, replay, and automation are refused. |
| Deployment, SQL-test, and lifecycle roles | Roles held by the first-manual operator only for the exact active `firstManualCertificationAttemptId` | Existing subscription Owner governs ARM; User Access Administrator is limited to an expressly approved role assignment; logical-server Entra administrator governs SQL bootstrap and data plane. No role on one plane grants the other. |
| Reviewers | Review target evidence, security design, deployment evidence, and implementation when it exists | Review neither supplies credentials nor grants cloud-operation authority. |
| Malicious or mistaken user/process | Untrusted | Must be unable to broaden public reachability, substitute a target, exfiltrate secrets, or mutate data without the applicable gates. |

Microsoft Entra is the only permitted authentication shape. The sealed Bicep authentication object identifies the owner as logical-server administrator and contains no runtime credential. The D-022 first-manual exception resolves policy, not protected live proof: the authenticated user, exact grants, and sign-in evidence remain operation-time gates. UAMI is expressly rejected; no copied token, password, client secret, embedded credential, or fabricated managed-identity flow may fill the gap.

No production, customer, or other pre-existing data is authorized. The readable fixture-value grammar is **unbounded** pending `U-007`: each future baseline/test-created row must have a recognizable persisted value under `SYS-15`, but no literal format is selected here. Minimize retention by preserving sanitized manifest differences, digests, state, and attempt evidence before considering a diagnostic hold.

No password data is in scope. If one is ever introduced, it must use a salted, memory-hard password KDF and be hashed, never encrypted. The workspace's general-purpose hashing utilities must never be used for credentials.

The complete closed version-2 lifecycle-policy object is integrity-sensitive. `EFTools.LifecyclePolicy.JCS.v1` validates schema before canonicalization, uses RFC 8785, permitted Unicode NFC and field-specific ASCII rules, canonical UTC/USD strings, UTF-8 without BOM or trailing LF, and lowercase SHA-256. Every producer must produce byte-identical canonical bytes; unknown, duplicate, missing, null, mistyped, alternate-encoding, or selected-field-only representations are refused. The digest is evidence of the complete object, not authority to create, wave, clean up, or tear down.

| B2: Secret delivery to harness process | Approved Entra-compatible connection/credential material enters the selected process | Secret disclosure, token replay, secret persistence, a UAMI or embedded-password workaround | `U-001` resolution before runnable use; no UAMI; opaque bounded-memory inputs; no child-process forwarding or caches; recursive redaction and canary validation; crash dumps are sensitive and not retained without separate authority. |
| B3: Harness to Azure SQL data plane | Harness uses explicit `SqlServer` plus `AzureSql` selection to exact reviewed FQDN and `ProphetsWay.Example` | Target substitution, downgrade to local/SQLite, TLS bypass, unauthorized public access, SQL overreach | Pre-network canonical binding to active evidence digest; exact case-sensitive database and FQDN comparison; encrypted transport and certificate validation; one public firewall address with start=end; distinct fixed-data and lifecycle paths. |
| B4: Fixed database to lifecycle-control authority | Operations read/update state, attempts, ledger, target binding, manifests, and survivor records | State forgery, authority split-brain, destructive action after stale/outage state, lost provenance | One append-only revision chain; owner-only activation; atomic one-active-revision rule; reconciliation before gates; strict non-mutating outage behavior; state/cause transition matrix. |
| B5: Process output to logs/run evidence | Harness, Azure client, tests, and operators emit diagnostics/evidence | Connection/token/IP leakage, misleading self-attestation, altered/insufficient audit evidence | Allowlisted non-secret fields, reviewed digests, recursive exception redaction, EF sensitive logging disabled, no secret sinks, evidence binding to authority rather than process variables. |
| B6: Infrastructure supply chain | Bicep directly resolves released AVM modules | Floating or substituted module, unreviewed raw-resource behavior | Direct `br/public:` AVM modules with explicit released tag, owner-confirmed compatibility and recorded digest; raw resource only with reviewed capability-gap exception. |
| B7: First-manual ratification to authority | Independently reviewed requirements/threat-model digests and protected current-pricing evidence form one immutable aggregate record | Self-ratification, stale pricing, changed policy, replay, or an implied spend cap | Owner ratifies only after `GATE-01` and accepted `GATE-02`; bind one `firstManualCertificationAttemptId`, both reviewed digests, USD 5.00, `coveredCumulativeAttempts=128`, pricing age no more than 24 hours, unbounded-tail acceptance, monitoring, and escalation. |
| B8: Lifecycle authority to disposable database | A separately approved wave or narrow stopped-state remediation evaluates policy, limits, ledger identity, and managed-risk state before SQL mutation | Database multiplication, cross-wave/foreign deletion, threshold bypass, or cleanup without authority | D-025 ordinal 1 permits one process, 8 concurrent, 128 cumulative creates, 15-minute database lifetime, and 180-minute wave lifetime. Only exact survivor inspection/cleanup or final teardown can later be considered, with D-018, fresh attempt, approval, and current gates. |

| First-manual wave ordinal 1 | Fresh wave attempt and approval, current protected identity/address, reconciled authority, canonical matching policy, pricing, daily review, `Eligible`, and `CreateWaveOpen` | `D-022` through `D-025`, `D-028`, `D-029`, and `HAR-12`; limits are admission checks, not standing authority. |

A tag, a prefix, a control connection, an expired hold, a cleanup deadline, continuing cost, or physical survival is never authorization to delete.

The address firewall rule persists for fixture lifetime once deployed. Its protected observation is fresh only at preview pre-submission and each wave pre-admission when certain synchronized-host UTC age is $0 \leq age \leq 5$ minutes and no backward-clock discontinuity or change in protected input set, authenticated egress context, network path/configuration, operation attempt, or target binding occurred. Failure requires a new protected input set, preview, review, and deployment approval; it never permits a range, second address, Azure-services-wide rule, or automatic widening.

## Abuse Cases

| Actor and goal | Path | Required response |
| --- | --- | --- |
| Compromised operator broadens fixture reachability | Adds range, second, Azure-services-wide firewall rule, or private-network alternative | Require exactly one public global-unicast IPv4 scalar with identical start/end; reject all alternatives before resource creation; deployment review checks graph cardinality. |
| Misconfigured harness certifies the wrong target | Supplies self-consistent endpoint/connection string for local, alias, or other database | Bind to active reviewed target record and authority digest; canonicalize before network; reject aliases, ports, local endpoints, case variants, and any mismatch. |
| Runtime user abuses owner-administrator metadata | Treats administrator object as credential or deploy/test identity | Seal object to metadata; reject runtime credentials/UAMI; block live operation until `U-001`/`U-002` resolve. |
| Cleanup defect deletes a valuable database | Matches only a prefix or uses broad catalog/control credentials | Require exact active-wave ledger identity, server, revision, fresh cleanup attempt, and approval; refuse fixed/system/foreign/cross-wave identities. |
| Interrupted wave contaminates later evidence | Starts a new wave after partial, failed, or uncertain state | Cause-preserving `Contaminated`/`Unknown` quarantine; only admitted recovery/restoration reaches `Clean`; a probe cannot clear cause. |
| Authority outage pressures emergency deletion | Cost or expiry motivates cleanup/teardown while provenance is unavailable | Refuse all mutation; record non-mutating evidence only; require reconciled active revision, fresh attempt, and owner approval. |
| Repeated disposable failures create unbounded cost | Sequential survivors bypass concurrent ceiling | On the default D-017 branch, reserve $C \times U$ for every cumulative create attempt and reject `Unbounded` or incomplete cessation evidence. The sole D-026/D-029 first-manual exception may accept `UnboundedAccepted` only through the active ratification and create admission predicates in the authorization rule, including D-018 and separate approval; unresolved survivor blocks new creates and never grants cleanup/deletion authority. |
| Diagnostic workflow turns retained failure into undeclared retention | Treats expired or second survivor as an approved hold | Only one evidence-backed owner-approved hold up to 24 hours; classify every other/expired/unknown survivor as `InvoluntaryUnresolved`, ledger and cost it, block creates. |
| Failure diagnostic leaks access material | Nested exception, EF logging, `.trx`, report, or console includes token or connection string | Recursive redaction across all sinks; sensitive logging disabled; canary tests cover raw, quoted, escaped, URL-encoded, and base64 forms. |
| Supply-chain substitution changes infrastructure semantics | Uses floating AVM module or unreviewed raw resource | Pin released AVM tag and record resolved module digest; capability-gap exception is required for raw resources. |
| Operator reuses a convenient identity after closure | Uses a wave ID, principal, or earlier approval as the D-022 exception | Require one authority-bound aggregate ID, activate it once, permanently consume it, and refuse another identity, replay, or automation without a newly approved requirements/threat-model cycle. |
| Address changes after a seemingly recent observation | Reuses the firewall input after network, egress, attempt, target, or clock context changes | Re-evaluate the inclusive five-minute predicate and its invalidators before preview/wave; refuse instead of widening reachability. |
| A lower later-wave limit is mistaken for ratified coverage | Proposes a replacement policy without derivation/approval or over 128 | Preserve immutable coverage 128; require fresh derivation and separate approval for 1..128; refuse above 128 pending newly reviewed ratification. |
| Threshold pressure drives unauthorized cleanup | Treats USD 5.00, expired hold, or continuing bill as permission to delete | Terminally stop creates/waves, dispatch and acknowledge an incident, retain continuing-cost status, and allow only the narrow separately approved remediation/teardown path after reconciliation. |
| Policy digest is reproduced over a different representation | Hashes source bytes, selected fields, or semantically equivalent JSON | Schema-validate the full object and require the JCS v1 canonical byte/digest vectors before operation admission. |

## Required Mitigations By Priority

1. **P0 - Live-operation gate enforcement:** Refuse every live connection, lifecycle action, preview, deployment, DACPAC, wave, recovery, cleanup, and teardown until its applicable `U-001` through `U-006`, fresh attempt, owner approval, and reconciled authority conditions hold. This defends against unauthorized cloud/data mutation and accidental spend.
2. **P0 - Sole authority integrity and availability:** Implement an append-only, digest-linked control authority with exactly one activatable revision and non-mutating outage behavior. This defends against split-brain, stale approval, lost cleanup history, and pressure-driven destructive action.
3. **P0 - Fixed database state machine:** Enforce the closed state/cause taxonomy, exact baseline proof, and operation admission before provider submission. This defends against cross-wave contamination and recovery/teardown authority confusion.
4. **P0 - Least-privilege identity separation:** Keep owner administration, ARM deployment, fixed-data test, and disposable lifecycle permissions separate. This defends against a broad control-plane credential becoming database-delete or test authority; exact grants await `U-001`/`U-002`.
5. **P0 - Secret-safe target binding:** Validate selectors, inputs, parsed connection, exact FQDN, exact `ProphetsWay.Example`, active evidence digest, TLS, and certificate validation before network access. This defends against credential leakage, wrong-target certification, and transport interception.
6. **P1 - One-address public exposure:** Create exactly one firewall rule for the owner-approved current public address, with no range, Azure-services rule, or automatic widening. This defends against unauthorized internet reachability; the actual address remains under `U-003`.
7. **P1 - Ledger and cost-bound disposable lifecycle:** On the default D-017 branch, require pre-create ledger registration, immediate successful cleanup, disjoint hold/survivor states, creation blocking, and $M = F + N + (C \times O) + (R \times H) + (C \times U)$ with finite per-attempt cessation proof. The sole D-026/D-029 first-manual `UnboundedAccepted` exception remains limited to the authorization rule's active ratification, pricing/backup, USD 5.00 terminal-state, exact aggregate/policy/target/operation, D-018, and separate-approval gates; it is not a finite-cost claim or cleanup/deletion authority. This defends against foreign deletion, orphaned databases, and understated cumulative cost.
8. **P1 - Evidence and diagnostic secrecy:** Allowlist non-secret evidence, redact recursively, disable EF sensitive-data logging, and validate canary absence from all durable/observable sinks. This defends against token, connection string, IP, and identity disclosure during failure handling.
9. **P1 - Direct pinned AVM composition:** Record module path, released tag, and resolved digest; require review for a raw-resource capability gap. This defends against unreviewed infrastructure supply-chain drift.
10. **P0 - First-manual aggregate and plane separation:** Bind every exception operation to one permanently consumed aggregate identity, interactive human Entra sign-in, and separate ARM/SQL authorities. This defends against identity replay, copied-token workarounds, standing automation, and cross-plane privilege inference.
11. **P0 - Managed-risk stop and incident control:** Enforce the immutable USD 5.00 terminal create/wave trigger, all non-threshold stop triggers, incident dispatch/acknowledgement, and D-018 non-mutation. This defends against unbounded additional exposure and pressure-driven deletion.
12. **P0 - Full-object lifecycle policy integrity:** Require schema-first `EFTools.LifecyclePolicy.JCS.v1` canonical bytes and a matching complete-object digest at authority, ratification, wave, and attempt. This defends against policy substitution and ambiguous cross-producer representations.
13. **P1 - Exact bounded first-manual lifecycle:** Enforce 14-day fixture lifetime, seven-day backup retention, daily owner review, one conditional 24-hour hold, and ordinal-1 8/128/15/180 limits. This defends against retained data/cost and uncontrolled database multiplication without claiming a financial cap.

| Gate | Unresolved owner input | Risk while unresolved | Required disposition |
| --- | --- | --- | --- |
| Protected live gates derived from U-001/U-002 | Exact authenticated human principal, ARM/SQL grants, and operation approval evidence | Role overreach or unusable authentication | D-022 settles first-manual policy only; protected live verification remains required for every operation. |
| Protected live gates derived from U-003 | Exact public IPv4 and observation/check evidence | Incorrect public reachability or PII disclosure | D-023/D-028 settle the predicate; literal/timestamps stay protected and a changed context requires a new preview/review/approval path. |
| Protected live gates derived from U-004/U-005 | Exact start/expiry, reviews, hold evidence, and actual limits/counts/timing | Retention failure, unowned monitoring, or database multiplication | D-024/D-025/D-029 settle policy; evidence must still be current and complete. |
| Protected live gates derived from U-006 | Current offer/pricing, backup treatment, accrued cost, and current owner approval | Incorrect financial assessment or unbounded-tail acceptance without informed ratification | USD 5.00 is a terminal trigger, never a cap. `U-007` remains a separate test-value design stream: it blocks literal readable fixture values, not this topology or threat model. `U-008` remains a convention-publication stream: it blocks cross-repository convention work, not use of the settled fixture names here.

Residual risk remains for the public endpoint even with a single exact address: the allowed endpoint can be probed from that address or become unreachable when egress changes. The model accepts no compensating automatic widening. Residual cost risk remains for a failed or unknown Azure operation and the explicitly accepted unbounded billing tail. USD 5.00 atomically sets `Stopped` and terminal `CreateWavePermanentlyExhausted` for this ratification; it stops additional creates/waves but cannot cap billing, erase survivors, or authorize cleanup. The model accepts no emergency destructive bypass and requires visible continuing-cost evidence, incident dispatch/acknowledgement, and normal authority restoration before any narrowly authorized mutation.

`D-027` is planning context only and selects neither current pricing, threshold, ratification, nor a live operation. `U-007` and `U-008` remain separate: readable fixture-value grammar and convention publication do not become implied by this amendment. `DOC-MR-001`, current pricing/offer/backup treatment, post-review owner ratification, protected values, exact what-if/deployment, and human execution remain unresolved and non-authorizing.
